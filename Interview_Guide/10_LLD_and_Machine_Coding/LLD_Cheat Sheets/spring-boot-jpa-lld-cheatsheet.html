01 · Request

POST /accounts/42/deposit with JSON.

02 · Bind

Spring turns JSON into a request DTO.

03 · Coordinate

Service validates and starts a transaction.

04 · Persist

Repository loads a managed entity; JPA tracks changes.

05 · Respond

Commit succeeds, then controller returns HTTP response.

C

Controller: translate

Understand HTTP, bind request data, choose response status. Avoid putting multi-step business rules here.

S

Service: coordinate

Apply a use case across objects, repositories, and external dependencies. Define transaction boundaries here.

R

Repository: persist

Find and save data. Keep business decisions out of SQL/repository methods when they belong to the domain.

Section 02

Core Spring Boot annotations

Open a card to see purpose, when to use it, an interview explanation, and a common mistake. Search filters cards too.

@SpringBootApplication

Does: Combines configuration, auto-configuration, and component scanning.

Use: On the application entry class, ideally in a root package above components.

Interview: “It bootstraps Spring and scans my application components from this package downward.”

Common mistake: Putting the main class in a sibling/nested package that misses components.

@SpringBootApplication public class App { public static void main(String[] args) { SpringApplication.run(App.class, args); }}
@RestController

Does: Registers a controller and treats return values as response bodies (`@Controller` + `@ResponseBody`).

Use: For JSON/API endpoints.

Interview: “This is the HTTP adapter between clients and application services.”

Mistake: Returning persistence entities directly can leak fields and cause lazy-loading/serialization problems.

@RequestMapping

Does: Maps a class or method to URL paths and optional HTTP conditions.

Use: Common prefix at class level; method-level mapping for endpoint details.

Interview: “It declares which HTTP requests are routed to this controller.”

Mistake: Confusing a route mapping with authorization; mapping alone does not secure an endpoint.

@RequestMapping("/api/accounts")
@GetMapping

Does: Maps an HTTP GET request.

Use: Read/query data; GET should not perform a business state change.

Interview: “A safe read endpoint; repeated calls should not mutate server state.”

Mistake: Using GET to deposit money or trigger a state-changing action.

@PostMapping

Does: Maps HTTP POST.

Use: Create resources or invoke non-idempotent actions such as a deposit request.

Interview: “POST submits a command/resource creation to the API.”

Mistake: Assuming POST automatically prevents duplicate submissions; use idempotency keys for sensitive retryable operations.

@PutMapping

Does: Maps HTTP PUT, conventionally replacing/upserting a resource representation.

Use: Full replacement where repeating the same request has the same effect.

Interview: “PUT is intended to be idempotent.”

Mistake: Treating PUT and PATCH as identical; PATCH usually represents partial modification.

@DeleteMapping

Does: Maps HTTP DELETE.

Use: Request resource deletion/deactivation.

Interview: “The controller maps the resource-oriented delete operation; service enforces domain rules.”

Mistake: Ignoring authorization, ownership checks, or referential constraints.

@RequestBody

Does: Deserializes the request body (often JSON) into a Java object using message converters.

Use: POST/PUT/PATCH input DTO.

Interview: “Spring binds JSON to a typed request object.”

Mistake: Taking a JPA entity directly and allowing clients to set server-owned IDs or privileged fields.

@PathVariable

Does: Binds a path segment to a parameter.

Use: Resource identity, such as `/accounts/{id}`.

Interview: “The identifier is part of the resource URL.”

Mistake: Confusing it with a query parameter or forgetting conversion/error behavior for invalid IDs.

@GetMapping("/{id}") AccountDto get(@PathVariable Long id)
@RequestParam

Does: Binds query-string or form parameters.

Use: Filters, paging, optional flags: `/accounts?status=ACTIVE`.

Interview: “Query parameters refine a collection query; path variables identify a resource.”

Mistake: Forgetting required/default-value behavior.

@Service

Does: Registers a service-layer component for dependency injection.

Use: Business use-case coordination.

Interview: “It marks application/service logic as a Spring bean.”

Mistake: Assuming the annotation itself creates a transaction; transaction behavior needs `@Transactional` and a proxy boundary.

@Repository

Does: Marks persistence components; Spring may translate persistence exceptions into its data-access exception hierarchy. Spring Data repository interfaces are detected automatically.

Use: Custom DAO classes; Spring Data interfaces extend `JpaRepository`.

Interview: “It marks persistence boundary and supports exception translation.”

Mistake: Writing business workflows inside repositories.

@Component

Does: Generic stereotype registered as a Spring bean.

Use: Helpers that do not fit service/controller/repository roles.

Interview: “Spring discovers and injects this component.”

Mistake: Annotating a class outside component scan and expecting it to be injected.

@Configuration

Does: Declares a class containing bean definitions/configuration.

Use: Explicit application wiring and framework configuration.

Interview: “This is code-based configuration for the Spring container.”

Mistake: Creating beans already provided by auto-configuration without a reason.

@Bean

Does: Registers the return value of a method as a Spring bean.

Use: Third-party classes or customized instances you cannot annotate.

Interview: “The container manages this object even though its class is external.”

Mistake: Calling a plain factory method and assuming the returned object is managed; it must be invoked as a bean method in configuration.

@Autowired

Does: Requests dependency injection by type (with qualifiers when needed).

Use: Usually unnecessary on a single constructor—Spring injects it automatically.

Interview: “Constructor injection makes required dependencies explicit and supports immutability.”

Mistake: Field injection hides dependencies and makes plain unit testing harder.

@RequiredArgsConstructor

Does: Lombok annotation that generates a constructor for `final` and `@NonNull` fields. It is not a Spring annotation.

Use: Reduce constructor boilerplate when Lombok is enabled.

Interview: “Spring injects the generated constructor; required collaborators remain final.”

Mistake: Expecting it to include ordinary non-final fields or forgetting Lombok annotation processing in the build/IDE.

Beginner default: use constructor injection. With one constructor, modern Spring does not require `@Autowired` on it.
Section 03

JPA entity cheat sheet

An entity is a Java object JPA maps to a database table. An entity is not automatically a safe API request/response object.

Common mapping annotations

AnnotationMeaningTypical use
@EntityManaged persistent classClass mapped to a table
@TableTable name/schema/constraintsCustomize database mapping
@IdPrimary keyExactly one entity identity
@GeneratedValueKey generation policyIdentity/sequence strategy
@ColumnColumn mapping/constraintsName, nullable, length, unique
@EnumeratedEnum persistence formatPrefer EnumType.STRING
@TransientNot persisted by JPADerived/temporary entity field

Entity → SQL picture

@Entity @Table(name = "bank_accounts") class BankAccount { @Id @GeneratedValue(strategy = IDENTITY) Long id; @Column(nullable = false) BigDecimal balance; @Enumerated(EnumType.STRING) AccountType type; }
bank_accounts
────────────────────────
id BIGINT PRIMARY KEY GENERATED
balance NUMERIC(...) NOT NULL
type VARCHAR(...) NOT NULL

JPA provider generates SQL based on mappings and schema strategy. Exact SQL depends on provider, dialect, and database.

Entity rules interviewers expect

Entities need an identifier and a no-argument constructor (public or protected). Prefer explicit column types/precision for money. Use `EnumType.STRING`, since enum ordinals can change meaning when constants are reordered. `@Transient` fields are not stored; Java's `transient` keyword is related serialization behavior, not an interchangeable JPA mapping.

Relational databases implement many-to-many through a join table. If the association needs fields such as enrolledAt, grade, or quantity, model the join as its own entity instead of bare `@ManyToMany`.

Section 05

`mappedBy` deep dive

`mappedBy` names the Java field on the other entity that owns the relationship. It is not a database column name.

Customer (inverse side)

@OneToMany(mappedBy="customer")
List<BankAccount> accounts
inverse → ownermappedBy points to field name

BankAccount (owning side)

@ManyToOne
@JoinColumn(customer_id)
Customer customer
customers
id PK
← FK lives here →
bank_accounts
id PK
customer_id FK

Owner side

The side with `@JoinColumn`; it controls the FK value written to the database. Here: `BankAccount.customer`.

Inverse side

The side with `mappedBy`; it mirrors the relationship. Here: `Customer.bankAccounts`.

Keep both in sync

Helper methods should set the account's customer and update the customer's collection.

// Customer: inverse side @OneToMany(mappedBy = "customer") private List<BankAccount> bankAccounts; // BankAccount: owning side (field name is exactly "customer") @ManyToOne @JoinColumn(name = "customer_id") private Customer customer;
What does “Can't find inverse attribute” / mappedBy error usually mean?

For `mappedBy = "customer"`, JPA searches for a Java relationship field named `customer` on `BankAccount`. It does not search for a SQL column called `customer_id`.

Check: exact case-sensitive field name; field exists on the other entity; it is annotated as the matching relationship; relationship target type is correct; no stale build classes. Typical Hibernate message: `mappedBy reference an unknown target entity property`. Spring Data derived-query errors about “no property” can look similar but arise from a repository method name, not `mappedBy`.

Common mistake: `mappedBy="customer_id"` when the Java field is named `customer`.

Section 06

Fetch strategies: LAZY vs EAGER

Choose what data to load and when. Fetch configuration can affect performance and query count.

LAZY load on access

Find account
Query 1: SELECT account ...

What can happen? watch the log

Initial queryAccount only
When customer is accessedAnother SELECT
Risk to watchN+1 / lazy outside transaction

Banking example

Load account and update its balance. If customer details are not needed, LAZY avoids fetching the customer row. If needed, use a deliberate fetch join/entity graph/query plan.

Shopping Cart example

Load cart, then items and product details. Loading many carts and lazily touching each product can produce N+1 queries. Fetch exactly the data required for the response.

LAZY is a fetch preference, not a guarantee that every access always emits a query. The persistence context may already contain the entity, and proxies/provider behavior matter. Avoid solving N+1 by making every relation EAGER; use query-specific fetch plans.
Section 07

DTO pattern: API shape ≠ database shape

Data Transfer Objects define what crosses a boundary; entities model persisted domain state.

Request JSONclient-controlled values
→
Request DTOvalidate allowed input
→
Service mappingapply domain rules
→
Entitydatabase state

Request DTO

Only fields the caller may submit. Example: `accountId`, `amount`; never accept balance-after-deposit as trusted input.

Response DTO

Only fields the caller may see. Hide secrets, internal flags, and relationships that should not be serialized.

Entity

JPA-managed state and persistence mapping. Can contain relationships, IDs, and internal fields unavailable in the API contract.

Safer request

record DepositRequest( Long accountId, @Positive BigDecimal amount ) {}

Why not bind the entity?

A caller could try to set `id`, `balance`, account owner, or future privileged fields. Direct entity responses can expose data or recurse through bidirectional associations.

Section 08

Repository layer

Spring Data generates common data-access implementations from an interface.

CrudRepository vs JpaRepository

CrudRepository<T, ID> offers basic CRUD operations. JpaRepository<T, ID> adds JPA-specific capabilities such as flushing and batch-oriented methods. Choose the abstraction your app actually needs.

interface AccountRepository extends JpaRepository<BankAccount, Long> { Optional<BankAccount> findByAccountNumber(Long number); }

Common operations

MethodMeaningRemember
save(entity)Persist/merge entity stateNot a business transaction by itself
findById(id)Optional resultHandle not found explicitly
findAll()Read all rowsBeware large/unbounded result sets
deleteById(id)Delete by IDCheck authorization/references
@QueryDeclare JPQL/native queryBind params; avoid string concatenation
@LockLock query resultUse within a transaction
Managed entity note: inside a transaction, changing a managed entity is usually detected by dirty checking at commit. Calling `save()` again may be unnecessary for that managed instance, though it can make intent explicit.
Derived query or `@Query`?

Use derived methods for simple, readable lookups (`findByStatusAndCreatedAtAfter`). Use `@Query` when the query shape is complex, a fetch join is needed, or the derived name becomes hard to understand. Prefer DTO projections for read views when loading a full entity graph is wasteful.

Section 09

Transactions: commit or rollback together

A transaction groups related database changes into one logical unit.

Account A− $200
→
@Transactionalone unit of work
→
Account B+ $200
→
Commitboth persist
Success: debit and credit both commit.
Failure: an exception triggers rollback according to rollback rules; neither change should persist.

Transfer service sketch

@Transactional public void transfer(Long fromId, Long toId, BigDecimal amount) { var from = accounts.findByIdForUpdate(fromId) .orElseThrow(); var to = accounts.findByIdForUpdate(toId) .orElseThrow(); from.withdraw(amount); to.deposit(amount); }

Interview details

Default rollback is for unchecked exceptions and Errors; checked exceptions need explicit rollback configuration. Spring transaction advice commonly works through proxies, so self-invocation can bypass it. Keep the method public and call it through the Spring bean boundary.

A database transaction cannot automatically undo an external payment/email. Distributed workflows may need an outbox, retries, or saga compensation.

Section 10

Concurrency & locking simulation

Two requests read the same balance, then both try to withdraw. Without coordination, one update can overwrite the other.

Balance = $100

Request A reads 100.

Same time

Request B also reads 100.

A computes

100 − 80 = 20.

B computes

100 − 80 = 20.

Lost update

Both report success; stored balance may be 20, not −60. Money was spent twice.

A locks row

SELECT ... FOR UPDATE.

B waits

Cannot update same row yet.

A commits

Balance becomes 20; lock released.

B resumes

Reads 20, rejects withdraw 80.

Safe result

Only one withdrawal succeeds.

@Lock(PESSIMISTIC_WRITE) @Query("select a from BankAccount a where a.id = :id") Optional<BankAccount> findByIdForUpdate(Long id);
Version = 7

A and B read version 7.

A updates

Writes balance and version 8.

B update

Expected version 7; row is now 8.

Conflict

One update fails with optimistic-lock exception.

Retry/return

Reload and re-evaluate safely.

@Version private long version;

Pessimistic

Lock now; competing transactions wait. Good for high contention/short critical sections. Can reduce throughput and cause deadlocks if lock ordering is inconsistent.

Optimistic

Allow concurrent reads, detect conflicting writes with `@Version`. Good when conflicts are uncommon. Caller must handle/retry conflict; retry only safe, repeatable work.

Always keep locking queries inside a real transaction. Locking a database row is not the same as synchronizing a Java method, and a JVM lock does not coordinate multiple application instances.
Section 11

`BigDecimal` vs `double` for money

Binary floating point cannot represent many decimal fractions exactly.

double approximate

0.1 + 0.2
→
0.30000000000000004

Binary floating point approximation can leak into financial calculations.

BigDecimal decimal-safe

new BigDecimal("0.10")
+
new BigDecimal("0.20")
=
0.30

Use string/decimal construction, explicit scale, and a rounding policy.

BigDecimal amount = new BigDecimal("12.50"); BigDecimal total = unitPrice.multiply(BigDecimal.valueOf(quantity)); BigDecimal rounded = total.setScale(2, RoundingMode.HALF_UP);
Never use `new BigDecimal(0.1)` for user-entered money; it captures the binary approximation. Decide currency scale and rounding mode by business rules. Minor-unit integers can also work, but require careful currency handling.

LLD thinking framework

Do not start by writing classes from nouns. Clarify behavior and rules first, then connect objects.

Identify entities/value objectsFind identity, state, lifecycle, and immutable concepts—not every noun.
Write invariantsExample: balance cannot go negative; one seat has at most one active booking.
Identify relationshipsAssociation, cardinality, ownership, and foreign-key side.
Define DTOs and APIsSeparate caller input/output from internal persistence entities.
Assign responsibilitiesEntity protects local invariant; service coordinates multi-object use case.
Walk success and failure flowsTrace reads, writes, transaction boundary, output, and unchanged state on failure.
Database & edge casesConstraints, duplicates, invalid input, concurrency, retries, and persistence.

Section 14

Common LLD interview prompts

Start with the invariant and main flow. Add patterns only where a real variation point exists.

Parking Lot

Core: ParkingLot, Floor, Spot, Vehicle, Ticket, Payment.

Relations: Lot → Floors → Spots; Ticket → Spot + Vehicle.

Invariant: One active vehicle per spot; no duplicate active ticket.

Hint: Separate allocation and pricing policies; release spot only after successful exit flow.

Library Management

Core: Book, BookCopy, Member, Loan, Catalog.

Relations: Book 1-to-many copies; Loan binds one member to one copy.

Invariant: At most one active loan per physical copy.

Hint: Keep title separate from a borrowable physical copy.

Banking System

Core: Customer, Account, Transaction/LedgerEntry.

Relations: Customer 1-to-many accounts; account 1-to-many entries.

Invariant: No invalid/negative debit; transfer debit and credit are atomic.

Hint: BigDecimal/minor units, transaction, locking, idempotency.

Food Delivery

Core: Customer, Restaurant, MenuItem, Cart, Order, Payment, Delivery.

Relations: Order has line items; each line snapshots product/price/quantity.

Invariant: Order lifecycle transitions are valid; payment/order state reconciles.

Hint: Strategy for pricing/assignment only if policies truly vary.

URL Shortener

Core: ShortLink, User, Alias, ClickEvent.

Relations: User may own many links; short key uniquely identifies destination.

Invariant: A key maps to one active destination within its namespace.

Hint: Clarify collision, expiry, custom alias, redirect, and analytics requirements.

BookMyShow

Core: Movie, Theatre, Screen, Seat, Show, ShowSeat, Booking, Payment.

Relations: ShowSeat ties a show to a physical seat and its availability.

Invariant: No double-confirmed seat for a show; holds expire.

Hint: Model hold/confirm/expire transitions and concurrency at the seat boundary.

Bonus gaps worth knowing

Validation, errors, N+1 & idempotency

These topics commonly distinguish a class diagram from a dependable backend design.

Validation & error mapping

Validate request shape at the API boundary (for example Bean Validation), enforce domain invariants in the model/service, and map known failures to clear HTTP responses with centralized exception handling. Never return stack traces to clients.

N+1 query problem

One query loads N parents; touching a lazy child for each parent can trigger N extra queries. Inspect SQL/query counts. Use fetch joins, entity graphs, batch fetching, or DTO projections for the specific use case.

Idempotency

Retries happen after timeouts even when the server already completed the action. For money movement/order creation, accept an idempotency key and persist its result under a uniqueness constraint.

Database constraints

App validation gives good errors; database constraints protect shared persisted state. Use NOT NULL, UNIQUE, CHECK, and foreign keys as appropriate. Keep schema migrations versioned in real projects.
