Section 03

Fetch type deep dive

Choose a fetch plan for a use case. “Load everything” is not a safe performance strategy.

SELECT accountAccount loadedCustomer proxy
LAZY: related customer data is fetched when accessed, if it is not already in the persistence context.

What the query visualization means

LAZY is a provider fetch hint. It can defer a query, but touching a lazy relationship outside an open persistence context can fail. Iterating over many entities and touching each relation can create the N+1 problem.

Banking: fetch customer only if the response needs customer data.
Shopping cart: fetch cart items/products intentionally for the cart view.
EAGER everywhere can transfer more rows, duplicate join data and increase memory. Prefer a deliberate query, entity graph, fetch join or projection.
Section 04

Banking system thinking

Money is a domain invariant, not a floating-point calculation in a controller.

Decimal precision intuition

double: 0.1 + 0.2→0.30000000000000004
BigDecimal("0.10") + BigDecimal("0.20")→0.30
Use decimal construction from strings, define scale and rounding policy. Alternative: integer minor units (cents/paise) with explicit currency handling.

Balance is not the whole ledger

Customeridentity
1 → *owns
BankAccountbalance + invariant
1 → *records
Transactionamount, type, time
A transaction/ledger entry explains why a balance changed, supports audit and reconciliation. A production ledger often treats entries as append-only and derives/reconciles balances.
Section 05

Concurrency thinking · stock = 1

Imagine 50,000 people trying to buy one phone. No engineer chooses a lucky thread by name; correctness depends on the atomic decision boundary.

Fifty thousand requests can arrive across threads and machines. A single process lock cannot coordinate every server.

Layer boundaries

Controller translates HTTP · Service coordinates use case/transaction · Entity protects domain state · Repository persists · Database enforces durable constraints.

JPA essentials

FK lives on owner side · mappedBy names Java field · fetch what use case needs · avoid N+1 · use DTOs at boundaries.

Concurrency checklist

State the invariant · identify shared state · make check+write atomic · choose DB lock/version/constraint · handle conflicts/retries/idempotency.

Money checklist

BigDecimal/minor units · validation · rounding policy · transaction/ledger · concurrency and auditability.

LLD answer order

Scope → actors → entities → invariants → relationships → API → flow → failure → concurrency → scale tradeoff.

Interview phrasing

“Given this invariant, I’ll enforce it at the state owner and make the database operation atomic because requests may race across instances.”
